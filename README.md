# Mini-CRM «Объекты и задачи»

Небольшая CRM для строительных объектов: постановщик заводит объекты и задачи и назначает исполнителей, исполнитель берёт свои задачи в работу и отправляет на проверку, постановщик принимает их или возвращает на доработку. Каждая смена статуса попадает в историю. Права доступа и правила переходов проверяет база данных, а не интерфейс.

Стек: React 19, TypeScript 6 (strict), Vite 8, Feature-Sliced Design v2.1, Supabase (Auth + PostgreSQL), shadcn/ui + Tailwind CSS v4, Motion, React Router 8, TanStack Query 5, React Hook Form + Zod 4.

## Быстрый старт (локально)

Нужны Node.js ≥ 22.22 и Docker (локальный Supabase).

```bash
npm ci
npm run db:start        # локальный Supabase в Docker, миграции применяются автоматически
npm run env:local       # создаёт .env.local с URL и publishable key локального стека
DEMO_PASSWORD=... DEMO_NEW_USER_PASSWORD=... npm run db:seed:demo   # демо-данные (bash / Git Bash; PowerShell — ниже)
npm run dev             # http://127.0.0.1:5173
```

Пароли демо-пользователей задаёте вы (в репозитории их нет). Требования Auth-сервера: не короче 8 символов, строчные и заглавные буквы и цифры. `DEMO_PASSWORD` — общий пароль трёх основных демо-аккаунтов, `DEMO_NEW_USER_PASSWORD` — пароль аккаунта «нового сотрудника». В PowerShell: `$env:DEMO_PASSWORD="..."; $env:DEMO_NEW_USER_PASSWORD="..."; npm run db:seed:demo`. Скрипт работает только с локальным стеком и только если демо-пользователей ещё нет; пересоздать данные: `npm run db:reset`, затем снова `db:seed:demo`. Создаётся 3 объекта и 8 задач во всех пяти статусах, часть с историей возврата на доработку.

Админ-панель локального Supabase (Studio): http://127.0.0.1:54323.

### Телефон в той же Wi-Fi сети (необязательно)

```bash
npm run dev:lan                      # определяет адрес в локальной сети
npm run dev:lan -- --ip=192.168.1.20 # или указать адрес вручную
```

Откройте напечатанный адрес на телефоне. Только для приватных сетей (скрипт отказывается работать с публичными адресами): в сети будут доступны приложение и локальный API Supabase. Брандмауэру ОС может потребоваться разрешить Node.js и порты 5173 и 54321 для частных сетей.

## Пользователи и роли

Открытой регистрации нет. Пользователей создаёт администратор.

Демо-логины (пароли — те, что вы передали при запуске сидинга):

| Email                   | Роль        | Примечание                                               |
| ----------------------- | ----------- | -------------------------------------------------------- |
| `manager@example.com`   | постановщик |                                                          |
| `executor1@example.com` | исполнитель |                                                          |
| `executor2@example.com` | исполнитель |                                                          |
| `newbie@example.com`    | исполнитель | «новый сотрудник»: при первом входе нужно сменить пароль |

### Как администратору создать пользователя

1. Studio → Authentication → Users → Add user → Create new user, указать email и пароль (по политике паролей), включить **Auto Confirm User**. Профиль создаётся автоматически, роль по умолчанию — исполнитель.
2. Сделать постановщиком (роль хранится в `app_metadata.app_role`, пользователь сам её изменить не может). В Studio → SQL Editor:

   ```sql
   update auth.users
      set raw_app_meta_data = raw_app_meta_data || '{"app_role": "manager"}'
    where email = 'user@example.com';
   ```

   Триггер синхронизирует роль в `public.profiles`. Допустимые значения: `manager`, `executor`; другое значение вызывает ошибку. Прямое изменение `update public.profiles set role = '…' where email = '…'` тоже работает, но источник истины — `app_metadata`: при следующей смене `app_role` там роль в профиле будет перезаписана. Поэтому используйте первый способ.

3. Исполнителя с назначенными задачами (в любом статусе, включая принятые) нельзя перевести в другую роль, пока задачи не переназначены: база откажет с ошибкой `assignee_has_tasks`.
4. Отображаемое имя берётся из `user_metadata.full_name`, иначе из части email до `@`.

### Смена пароля при первом входе

У каждого нового пользователя стоит флаг `must_change_password`. Пока пароль не изменён, пользователь видит только экран смены пароля, а база не отдаёт ему ни объекты, ни задачи, ни историю (это проверяет RLS, не интерфейс). Флаг снимает триггер БД при реальной смене пароля.

Сброс пароля администратором (Studio → Users) тоже меняет пароль и поэтому снимает флаг. Чтобы потребовать смену снова:

```sql
update public.profiles set must_change_password = true where email = 'user@example.com';
```

## Как защищены данные

- RLS включён на каждой таблице. Постановщик видит всё. Исполнитель видит только свои задачи, объекты, где у него есть задачи (и в них только свои задачи), и историю своих задач.
- Права на уровне колонок: клиент не может записать статус, автора и дату задачи, не может изменить объект уже созданной задачи, а также роль и флаг смены пароля.
- Статус меняется только функцией БД `change_task_status`. Она блокирует строку задачи, проверяет правило по таблице переходов (`task_transitions`, её же читает интерфейс), требует комментарий при возврате на доработку и в той же транзакции пишет историю. Параллельные запросы обрабатываются по очереди: второй увидит уже новый статус.
- Историю пишет только база; у клиентов нет прав на insert, update и delete для неё. Автор и время записи подставляет БД.
- Роль задаётся в `app_metadata` (клиент изменить её не может; `user_metadata` не используется), триггер копирует её в профиль, и правила доступа читают эту копию.
- Секретных ключей нет ни во фронтенде, ни в репозитории: браузер использует только publishable key, `service_role`/`sb_secret_*` отвергаются валидацией окружения и линтером. Секретный ключ локального стека нужен только node-скриптам и интеграционным тестам.
- Политику паролей применяет сервер Auth (8+ символов, строчные, заглавные, цифры), а не форма.

## Тесты

| Команда                    | Что проверяет                                                                                                         |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `npm run check`            | TypeScript, ESLint, Steiger (границы FSD), Prettier, unit и компонентные тесты                                        |
| `npm run test`             | Только unit и компонентные тесты                                                                                      |
| `npm run test:integration` | Прямые запросы к настоящему локальному Supabase от имени разных пользователей: обход интерфейса, RLS, переходы, гонки |
| `npm run test:db`          | pgTAP: схема, права, RLS, матрица переходов, история, профили                                                         |
| `npm run db:lint`          | Линтер SQL/plpgsql                                                                                                    |
| `npm run test:e2e`         | Playwright (Chromium, desktop и mobile) + проверка доступности axe                                                    |
| `npm run verify`           | Всё перечисленное, сборка и аудит зависимостей (`npm run audit`)                                                      |

Интеграционные, pgTAP и E2E-тесты требуют запущенного `npm run db:start`. Первый запуск E2E: `npm run test:e2e:install`.

## Решения и допущения

ТЗ неоднозначно в ряде мест; ответов работодателя не было, приняты такие допущения.

1. Постановщик редактирует название, описание и исполнителя задачи в любом статусе, кроме «Принята». Статус меняется только переходами, объект задачи не меняется.
2. Объект с задачами удалить нельзя (сначала задачи). Задачу удаляет только постановщик, вместе с её историей.
3. Любой постановщик может принимать и возвращать задачи другого постановщика («видит всё»).
4. Исполнитель при создании задачи обязателен.
5. Исполнителя можно переназначить постановщиком после взятия в работу; новый исполнитель продолжает с текущего статуса, переназначение в истории не фиксируется (история хранит только статусы).
6. Исполнитель видит в объекте только свои задачи.
7. Роль задаёт администратор в `app_metadata`, копия хранится в профиле и используется правилами доступа; клиент её менять не может.
8. Комментарий при других переходах необязателен, при возврате на доработку обязателен.
9. «Принята» — конечный статус.
10. Создание задачи пишется в историю первой записью (из «нет статуса» в «Новая»).
11. Один пользователь — одна роль.
12. Исполнитель видит имена людей, связанных с его задачами: авторов задач и тех, кто менял статус.

Прочие решения:

- «Пустой» текст — только ASCII-пробельные символы (пробел, табуляция, перевод строки и т. п.); Unicode-пробелы пустыми не считаются. Интерфейс строже (JS `trim`).
- Неизвестные адреса показывают страницу 404 и для анонимов: данных на ней нет.
- В демо-данных время в истории настоящее (все записи созданы вплотную друг к другу): даты не подделывались, история создана реальными вызовами от имени нужных ролей.
- Сброс пароля, 2FA и подтверждение email не реализованы: ТЗ их не требует.
- `profiles.email` не синхронизируется при смене email пользователя.
- Параметр `secure_password_change` выключен: смена пароля происходит при первом входе, сессия свежая. Для продакшена рекомендуется включить.

## Не сделано и ограничения

- Облачный деплой, публичная ссылка и публикация на GitHub зависят от решения владельца проекта.
- Нет сброса пароля и 2FA.
- Проверка паролей по базе утечек (leaked password protection) доступна только на платном тарифе Supabase, поэтому не включена.
- Unicode-пробелы не считаются пустыми.
- Кросс-браузерный E2E — только Chromium (desktop и mobile-эмуляция).

## Облачное развёртывание (подготовлено, пока не выполнено)

Шаги описаны для будущего запуска; ничего из этого ещё не сделано.

1. Создать проект Supabase. Применить миграции из `supabase/migrations/` (Supabase CLI: `supabase link`, `supabase db push` из репозитория, выполняет владелец проекта).
2. Authentication → Sign In / Providers: отключить регистрацию новых пользователей (Allow new users to sign up). Подтверждение email можно не включать.
3. Authentication → Policies: минимальная длина 8, обязательны строчные, заглавные буквы и цифры (как локально). По возможности включить «Secure password change».
4. Authentication → URL Configuration: указать Site URL (адрес хостинга) и добавить его в Redirect URLs.
5. Создать пользователей по инструкции выше (Studio → Add user + SQL для роли). Демо-скрипт `db:seed:demo` предназначен только для локального стека.
6. Статический хостинг (Vercel или Netlify): команда сборки `npm run build`, папка `dist`, fallback всех путей на `index.html` (SPA). Переменные окружения только две: `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Секретный ключ (`service_role`, `sb_secret_*`) в хостинг и в репозиторий не добавлять никогда.
