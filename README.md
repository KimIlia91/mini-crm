# Mini-CRM «Объекты и задачи»

Решение тестового задания: мини-CRM для строительной компании, в которой руководитель ставит задачи по объектам (стройкам), а исполнители выполняют их и отдают на проверку. Условия — в [техническом задании (Google Docs)](https://docs.google.com/document/d/1dpyRJ1E__eD0cisYSj0GDml4xtTTPaLe/edit?usp=sharing).

Что реализовано по заданию:

- две роли — постановщик и исполнитель — с разными правами;
- объекты и задачи: создание, редактирование, удаление, поиск, фильтр и сортировка;
- статусы задачи с фиксированными переходами и историей смены статусов;
- права доступа и правила переходов проверяет база данных (PostgreSQL, RLS), а не интерфейс: обойти их прямым запросом к API нельзя.

Сверх задания: изменения других пользователей появляются без перезагрузки страницы (Supabase Realtime), у каждого пользователя — свои уведомления: всплывающие сообщения и список под значком колокольчика.

**Демо:** https://mini-crm-seven-kappa.vercel.app (логины — в таблице ниже, пароли передаются отдельно).

**О проекте и видео-обзор:** https://mini-crm-seven-kappa.vercel.app/about (открывается без входа).

## Запуск локально

### Что установить

- **Node.js 22.22 или новее** — https://nodejs.org (проверить: `node -v`).
- **Docker Desktop** — https://www.docker.com/products/docker-desktop. Он должен быть **запущен** перед шагом 2: локальная база Supabase работает в его контейнерах.
- Supabase CLI ставить отдельно не нужно — он приходит с зависимостями проекта.

Все команды выполняются в папке проекта.

### Шаг 1. Установить зависимости

```bash
npm ci
```

### Шаг 2. Запустить локальную базу

```bash
npm run db:start
```

Первый запуск скачивает образы Docker и занимает несколько минут. Схема базы (таблицы, права, функции) создаётся из `supabase/migrations` автоматически. Когда всё готово, команда печатает адреса сервисов.

### Шаг 3. Подключить приложение к локальной базе

```bash
npm run env:local
```

Создаёт файл `.env.local` с адресом локальной базы и её публичным ключом. Файл не попадает в git; создавать его вручную не нужно.

### Шаг 4. Создать демо-пользователей и данные

Пароли придумайте сами — их нет в репозитории. Требование: не короче 8 символов, латинские строчные и заглавные буквы и цифры. Первый пароль — для постановщика и двух исполнителей, второй — для «нового сотрудника».

Windows (PowerShell):

```powershell
$env:DEMO_PASSWORD="MyDemoPass1"; $env:DEMO_NEW_USER_PASSWORD="MyStartPass2"; npm run db:seed:demo
```

macOS / Linux / Git Bash:

```bash
DEMO_PASSWORD=MyDemoPass1 DEMO_NEW_USER_PASSWORD=MyStartPass2 npm run db:seed:demo
```

В конце скрипт печатает созданные логины (см. «Демо-пользователи» ниже).

### Шаг 5. Запустить приложение

```bash
npm run dev
```

Откройте http://127.0.0.1:5173 и войдите, например, как `manager@example.com` с первым паролем из шага 4.

### Полезное

| Что нужно                          | Команда                                 |
| ---------------------------------- | --------------------------------------- |
| Начать данные заново               | `npm run db:reset`, затем снова шаг 4   |
| Остановить базу                    | `npm run db:stop`                       |
| Посмотреть таблицы и пользователей | Supabase Studio: http://127.0.0.1:54323 |

Если `db:start` пишет, что Docker недоступен, — запустите Docker Desktop и повторите. Если скрипт демо-данных пишет «демо-пользователи уже есть» — выполните `npm run db:reset` и повторите шаг 4.

## Демо-пользователи

Регистрации нет — пользователей создаёт администратор (локально и в облаке — скриптом демо-данных).

| Email                   | Роль                           | Пароль                                                              |
| ----------------------- | ------------------------------ | ------------------------------------------------------------------- |
| `manager@example.com`   | постановщик                    | `DEMO_PASSWORD`                                                     |
| `executor1@example.com` | исполнитель                    | `DEMO_PASSWORD`                                                     |
| `executor2@example.com` | исполнитель                    | `DEMO_PASSWORD`                                                     |
| `newbie@example.com`    | исполнитель, «новый сотрудник» | `DEMO_NEW_USER_PASSWORD` — при первом входе попросит сменить пароль |

Скрипт создаёт 3 объекта и 8 задач во всех пяти статусах; история переходов создаётся настоящими вызовами от имени нужных ролей.

## Проверки

| Команда                    | Что проверяет                                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `npm run check`            | типы, линтер, границы FSD, форматирование, unit-тесты                                                                  |
| `npm run test:db`          | pgTAP: схема, права, RLS, матрица переходов, история                                                                   |
| `npm run test:integration` | прямые запросы к локальному Supabase от разных пользователей в обход интерфейса                                        |
| `npm run test:e2e`         | сценарии ролей в браузере (desktop и мобильный) + доступность (axe); перед первым запуском: `npm run test:e2e:install` |
| `npm run verify`           | всё вместе + сборка и аудит зависимостей                                                                               |

`test:db`, `test:integration` и `test:e2e` требуют запущенного `npm run db:start`.

## Как защищены данные

- **RLS на каждой таблице.** Постановщик видит всё. Исполнитель — только свои задачи, объекты, где они есть, и историю своих задач.
- **Статус меняет только функция БД** `change_task_status`: проверяет роль и допустимый переход, требует комментарий при возврате на доработку, блокирует строку от гонок и в той же транзакции пишет историю.
- **История неизменяема:** у клиентов нет прав на её запись, изменение и удаление; автора и время подставляет база.
- **Удаление мягкое:** задачи и объекты скрываются, история сохраняется; восстановить или изменить удалённое через API нельзя.
- **Роль задаёт администратор** (`app_metadata`), пользователь изменить её не может. Пока не сменён первый пароль, база не отдаёт пользователю ни объектов, ни задач, ни истории: доступны только его собственный профиль и справочник допустимых переходов статусов (`task_transitions`).
- **Обновления в реальном времени:** база сама отправляет в приватные каналы только идентификаторы изменённых записей (`user:<id>` — пользователю, `role:manager` — постановщикам); подписку на чужой канал запрещает RLS, клиенты не могут отправлять сообщения. Данные приложение перечитывает обычными запросами под теми же правами. Если сигнал потерялся, данные обновятся при переподключении, возврате на вкладку или не позже чем через минуту.
- **Уведомления пишет только база** — в той же транзакции, что и событие; автор действия уведомление не получает. Пользователь видит только свои уведомления (RLS) и может лишь отметить их прочитанными; уведомления старше 90 дней удаляются по расписанию.
- **Секретных ключей нет ни во фронтенде, ни в репозитории:** браузер получает только публичный ключ; секретный отвергается проверкой окружения и линтером.

## Допущения по ТЗ

1. Постановщик редактирует название, описание и исполнителя задачи в любом статусе, кроме «Принята». Статус меняется только переходами.
2. Объект, в котором есть задачи (в том числе принятые), удалить нельзя. Удаление мягкое — история остаётся в базе.
3. Любой постановщик может принимать и возвращать любые задачи.
4. Исполнитель при создании задачи обязателен; переназначать можно, в историю статусов это не пишется.
5. «Принята» — конечный статус. Комментарий обязателен только при возврате на доработку.
6. Создание задачи — первая запись истории («— → Новая»).
7. Одна роль на пользователя. Сброс пароля, 2FA и подтверждение почты не делались — ТЗ их не требует.

## Развёртывание

- **База:** проект Supabase Cloud; миграции из `supabase/migrations` применяются интеграцией Supabase ↔ GitHub при push в ветку `prod`. В настройках Auth выключена регистрация, задана политика паролей и Site URL. В настройках Realtime выключен «Allow public access» (только приватные каналы); для очистки уведомлений нужно расширение pg_cron (Integrations → Cron).
- **Фронтенд:** Vercel, сборка `npm run build`, папка `dist`, переадресация путей на `index.html` — в `vercel.json`. Переменные окружения: `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
- **Демо-данные в облаке:** `node scripts/seed-demo.mjs --cloud` с переменными `SEED_SUPABASE_URL`, `SEED_SUPABASE_PUBLISHABLE_KEY`, `SEED_SUPABASE_SECRET_KEY` и паролями (запускает владелец проекта; секретный ключ остаётся только в его терминале).

## Структура

```
src/
  app/        точка входа, маршруты, оформление
  pages/      экраны: вход, смена пароля, объекты, объект, задача, мои задачи
  features/   действия пользователя (создание, редактирование, удаление)
  entities/   сущности: профиль, объект, задача, уведомление
  shared/     клиент Supabase, авторизация, общие компоненты и утилиты
supabase/
  migrations/ SQL-миграции — единственный способ менять схему
  tests/      pgTAP-тесты базы
scripts/      локальные утилиты: окружение, демо-данные, запуск в локальной сети
tests/        интеграционные и браузерные тесты
```
